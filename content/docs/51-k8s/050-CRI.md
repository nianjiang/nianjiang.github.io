# CRI

### Tools

容器运行时分为两层：**高层运行时（High-Level Runtime）** 实现 CRI 或 Docker Engine API，负责镜像拉取、存储、容器与 Pod 沙箱的生命周期管理；它把实际创建进程的工作交给 **低层运行时（Low-Level / OCI Runtime）**，后者实现 OCI Runtime Spec，直接调用内核的 namespace、cgroup 等能力。

#### High-Level Runtimes

| Name | Doc | Github | Note |
| :--- | :--- | :--- | :--- |
| [containerd](https://containerd.io/) | [Docs](https://github.com/containerd/containerd/blob/main/docs/getting-started.md) | [Github](https://github.com/containerd/containerd)| 行业标准的容器运行时，强调简单、健壮和可移植性；实现 CRI，可管理容器与 Pod 沙箱的完整生命周期，底层默认调用 runc 创建进程。 |
| [Docker](https://www.docker.com/) | [Docs](https://docs.docker.com/) | [Github](https://github.com/docker) | 最广为人知的容器平台，提供构建、分发和运行应用的完整方案；并非原生 CRI 实现，Kubernetes 中需通过 cri-dockerd 适配（dockershim 已于 v1.24 移除）。 |
| [Podman](https://podman.io/) | [Docs](https://docs.podman.io/) | [Github](https://github.com/containers/podman) | 无守护进程（daemonless）的容器引擎，CLI 兼容 Docker，常用于开发和构建场景替代 Docker；本身不是 CRI 实现，底层由 conmon 监督 crun/runc 创建容器。 |
| [CRI-O](https://cri-o.io/) | [Docs](https://cri-o.io) | [Github](https://github.com/cri-o/cri-o) | 一个轻量级的、专门为 Kubernetes 设计的容器运行时，只实现 Kubernetes CRI (Container Runtime Interface) 接口，进程创建同样委托给 OCI 运行时。 |
| [Kata Containers](https://katacontainers.io/) | [Docs](https://github.com/kata-containers/kata-containers/tree/main/docs) | [Github](https://github.com/kata-containers/kata-containers) | 安全容器方案，以 `containerd-shim-kata-v2` 形式插件式挂在 containerd / CRI-O 之下（也可通过 `--add-runtime` 挂到 dockerd），按 Pod 的 `runtimeClassName` 选择；镜像仍是标准 OCI 镜像，但每个 Pod 由一台轻量 VM 承载，底层 `kata-runtime` 见下方 Low-Level 表。 |



#### Low-Level Runtimes / OCI Runtimes

| Name | Doc | Github | Note |
| :--- | :--- | :--- | :--- |
| [runc](https://github.com/opencontainers/runc) | [Docs](https://manpages.debian.org/unstable/runc/runc.8.en.html) | [Github](https://github.com/opencontainers/runc) | OCI (Open Container Initiative) Runtime Spec 的参考实现与命令行客户端，负责设置 namespace 与 cgroup 并启动容器进程；containerd、CRI-O 默认使用它。 |
| [crun](https://github.com/containers/crun) | [Docs](https://manpages.debian.org/unstable/crun/crun.1.en.html) | [Github](https://github.com/containers/crun) | 用 C 语言实现的 OCI 运行时，是 runc 的轻量替代品，启动更快、内存占用更小，完整支持 cgroup v2；Podman v3默认使用它。 |
| [nvidia-container-runtime](https://github.com/NVIDIA/nvidia-container-toolkit) | [Docs](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/index.html) | [Github](https://github.com/NVIDIA/nvidia-container-toolkit) | NVIDIA Container Toolkit 提供的 OCI 运行时，本质是 runc 的包装层：启动前通过 libnvidia-container 把 GPU 设备、驱动库和二进制注入容器，支撑 `--gpus` 与 CRI 场景的 GPU 容器；旧版独立仓库已归档，现随 toolkit 一同发布。 |
| [runsc](https://gvisor.dev/) | [Docs](https://gvisor.dev/docs/) | [Github](https://github.com/google/gvisor) | gVisor 提供的 OCI 运行时：Sentry 作为用户态应用内核拦截并处理应用系统调用（不透传到主机内核），文件访问由 Gofer 代理，相当于合并的 guest kernel 与 VMM；安全性强，代价是 syscall 开销更高、部分接口兼容性不足。 |
| [kata-runtime](https://katacontainers.io/) | [Docs](https://github.com/kata-containers/kata-containers/tree/main/docs) | [Github](https://github.com/kata-containers/kata-containers) | Kata Containers 的 OCI 运行时：每个容器（或 Pod）跑在轻量级虚拟机中（QEMU / Cloud Hypervisor + guest kernel），兼顾 OCI 镜像兼容与虚拟机级隔离，隔离性最强；代价是启动更慢、内存开销更大，并要求宿主机支持虚拟化。 |
| [youki](https://github.com/youki-dev/youki) | [Docs](https://youki-dev.github.io/youki/) | [Github](https://github.com/youki-dev/youki) | 用 Rust 实现的 OCI 运行时，借助语言的内存安全减少处理系统调用时的风险；启动开销低于 runc、高于 crun，已从实验性项目成长为 CNCF sandbox 项目并有生产环境采用。 |

**组合用法：** 同一集群可通过 RuntimeClass 混用不同隔离级别——CRI-O 根据 Pod 的 `runtimeClassName` 把请求分派到对应 OCI 运行时（默认 runc/crun、Kata 强隔离、gVisor 沙箱）。节点上需预先安装对应的 handler，否则 Pod 会因找不到运行时配置而创建失败。
