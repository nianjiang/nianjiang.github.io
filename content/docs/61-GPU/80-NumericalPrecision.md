# 混合精度训练：NVIDIA《Train with Mixed Precision》要点

> 原文：[Train with Mixed Precision — NVIDIA](https://docs.nvidia.com/deeplearning/performance/mixed-precision-training/index.html)
> （NVIDIA Deep Learning Performance 系列，2023-02 版）
>
> **原文问题**：Why does numerical precision matter?

## 一句话结论

原文的论证是"三个收益 + 一条底线"：

| 收益 | 机制 |
| -------- | -------- |
| 显存 | 16 位比 32 位省一半，同样显存装下更大的网络或更大的 batch |
| 带宽 | 数据搬运量减半，访存受限的算子直接变快 |
| 算力 | Tensor Core 只吃低精度输入，V100 上 FP16 矩阵乘吞吐约为 FP32 的 4 倍 |

底线是**精度不变**。原文反复强调的措辞是 "identifying the steps that require full precision"：混合精度不是"全部换成 16 位算得快"，而是先找出必须用 FP32 的少数步骤，其余全部降到 FP16，从而在**不损失任务精度**的前提下拿到收益。2023 版给出的端到端加速上限是"最高约 3 倍"，作用于算术密集度最高的模型。

## 一、FP16 到底丢了什么

IEEE 754 半精度格式：1 位符号、5 位指数、10 位尾数，指数偏置 15（指数取值 0 和 31 被特殊值占用），因此正常数指数范围是 `[-14, 15]`。

| 格式 | 符号 | 指数 | 尾数 | 偏置 | 可表示范围（含次正规） | 十进制量级 |
| -------- | -------- | -------- | -------- | -------- | -------- | -------- |
| FP16 | 1 | 5 | 10 | 15 | `2^-24` ~ 65,504 | 约 6e-8 ~ 6.5e4 |
| FP32 | 1 | 8 | 23 | 127 | `2^-149` ~ 3.4e38 | 约 1.4e-45 ~ 3.4e38 |

原文在这里给了两个可直接记住的数字：

- FP16 的动态范围（含次正规）只有 **40 个 2 的幂**；FP32 含次正规是 **264 个 2 的幂**。
- FP16 能表示的最大值是 **65,504**，超了就变 inf —— 这个数字在全文中反复出现，是后面所有 scaling 决策的硬边界。

关键判断：**尾数从 23 位掉到 10 位不是主要矛盾，可表示范围被砍掉才是。** 10 位尾数相对误差约 `2^-11`，对训练来说通常够用；真正的杀手是最小可表示值抬高到 `2^-24`，小于它的量（尤其是梯度）直接变 0，而且往上限方向很容易溢出。

## 二、Tensor Core 为什么只吃低精度

Volta 引入的 Tensor Core 做的是 `D = A × B + C`：A、B 是 FP16 的 4×4 矩阵，C、D 可以是 FP16 也可以是 FP32 —— 也就是**乘是 16 位、累加器可以是 32 位**。这是"混合精度"在硬件层的原始含义。

量级对照（V100）：

| 指标 | 数值 |
| -------- | -------- |
| Tensor Core 数量 | 640 |
| FP16 理论峰值 | 约 120 TFLOPS |
| 相对 FP32 单精度流水线 | 约 4 倍（单看 matmul 流水线是 8 倍） |
| 相对 FP64 | 约 10 倍 |

所以矩阵乘和卷积（CNN 的绝对主体）能吃到这块算力，其余算子吃不到 —— 这一点直接决定了后文"端到端加速为什么远小于 8 倍"。

## 三、精度会不会掉：一个梯度直方图的案例

原文用 Multibox SSD（VGG-D backbone）的激活梯度直方图说明**为什么需要额外手段**：

1. 先统计 FP32 训练时全网络各层的激活梯度幅值，横轴取对数。
2. 其中 **66.8% 的值本身就是 0**，另有 4% 落在 `(2^-32, 2^-30)` 这个区间。
3. 直接转成 FP16 后，**31% 的梯度值变成 0**，只有 5.3% 保持非零 —— 对这个网络来说，这个丢法会直接导致训练发散。
4. 但 FP16 的可表示范围大量空着。把这些值整体平移几个指数位就能救回来：对该网络**平移 3 个指数位（即乘 8）就足以追平 FP32 的精度**。

这段是全文最有说服力的地方：FP16 的问题不是"精度不够"，而是"值域位置不对"。既然是位置问题，就可以用一次乘法修正 —— 这就是 loss scaling 的全部动机。

## 四、loss scaling：一次乘法解决值域问题

原理只有一句：**在前向算出 loss 之后、反向之前把 loss 乘以 S**。由链式法则，反向会把这个系数原样传给所有梯度，不增加任何反向计算量，却让原本掉到 0 以下的小梯度重新落进 FP16 可表示区间。

配套的两个细节是实操中最容易漏的：

- **权重梯度必须在更新权重前除回来**（乘 `1/S`），否则更新幅度和 FP32 训练不一致。位置选在**反向之后、梯度裁剪（和 weight decay 等任何梯度相关计算）之前**，这样裁剪阈值、正则系数等超参一个都不用改。
- **大规约的结果要留在 FP32**：BatchNorm 的均值/方差、SoftMax 属于此类。BatchNorm 依然可以 FP16 进 FP16 出（省一半带宽），只是统计量和数值调整要用 FP32 算。

原文给出的单次迭代流程（需要 FP32 主权重时）：

1. 维护一份 FP32 的主权重副本；
2. 迭代开始，从 FP32 主权重生成一份 FP16 副本；
3. 前向：FP16 权重 + FP16 激活；
4. loss × S；
5. 反向：FP16 权重、激活及其梯度；
6. 权重梯度 × `1/S`，再更新。

## 五、S 怎么选：常数、按统计量、还是动态

| 方式 | 做法 | 代价 |
| -------- | -------- | -------- |
| 常数 S | 原文实测网络取值范围 **8 ~ 32K**，且"很多网络根本不需要缩放" | 换网络、换框架、换 batch size 都要重新试 |
| 按梯度统计量 | 取 S 使 `S × max(|梯度|)` 小于 65,504 | 需要知道梯度分布 |
| 动态 S（推荐） | 用一个较大的 S 起步，每轮迭代重新评估：连续 N 步不溢出就把 S 加大；一旦溢出就**跳过这次权重更新**并把 S 减小 | 实现复杂，但迁移到新模型时无需重新调参 |

溢出为什么必须拦：梯度出现 inf/NaN 后，权重更新会**不可逆地**损坏权重。原文说这类溢出很容易在"乘 1/S 那一步"顺带检测出来，成本很低。另外它给了一个安抚性结论：只要跳过更新的频率不高，学习率 schedule 不需要为此专门调整。

## 六、自动混合精度（AMP）：把三件事交给框架

手工做混合精度要做三步，全部可以自动化：

1. 把模型里能用 FP16 的地方转成 FP16；
2. 保留 FP32 主权重来累积每次迭代的更新；
3. 加 loss scaling。

支持全自动的框架会把 **loss scaling 和主权重塞进 optimizer 类**，并**自动在 FP16/FP32 之间 cast**（该省的地方降精度，该保的地方升精度），对外只暴露一行代码或一个环境变量。原文点名 TensorFlow、PyTorch、MXNet 三家；底层靠 AllowList / DenyList / InferList 决定每个算子用什么精度，各框架的 DenyList 不一样。

> 一个值得注意的原文不一致：第 2 节说混合精度只需"two steps"（移植到 FP16 + loss scaling），第 3 节说"three steps"（+ FP32 主权重）。后者才是完整口径 —— 主权重在第 2 节是被当作"某些网络需要"的可选项讲的。

## 七、把 Tensor Core 用满：三步，收益递减

| 步骤 | 做法 | 复杂度 |
| -------- | -------- | -------- |
| 1. 满足形状约束 | FP16 矩阵乘的 M、N、K 都取 8 的倍数；INT8（Turing）取 16 的倍数；卷积输入/输出通道取 8 的倍数 | 低，但**收益最大** |
| 2. 提高算术强度 | 提高每个输入字节上的计算量，让 kernel 从访存受限变成计算受限 | 中 |
| 3. 减少非 Tensor Core 工作 | 剩下那部分算子手工优化或交给编译器 | 高 |

细节：

- **形状对齐**可以直接落到超参上：mini-batch 取 8 的倍数、linear 层维度取 8 的倍数、卷积通道数取 8 的倍数、分类任务把词表 padding 到 8 的倍数、序列任务把序列长度 padding 到 8 的倍数。
- **算术强度的门槛**可以算出来：V100 是 125 TFLOPS 算力配 900 GB/s 带宽，两者相除，**每个输入字节少于约 140 FLOP 的 kernel 必然是访存受限的**，Tensor Core 跑不满。提高办法：RNN 里把权重和门激活拼接、序列模型按时间维拼接激活；结构上偏好稠密运算（普通卷积的算术强度远高于 depthwise separable）。
- **别指望端到端等于 kernel 加速比**。原文的算术例子：假设一半训练时间花在 Tensor Core 加速的算子上，这些算子快 5 倍，端到端只有 `1 / (0.5 + 0.5/5) = 1.67x`。Tensor Core 占比越低，剩下的非加速算子越值得优化（手写 CUDA，或 XLA / PyTorch JIT 这类编译器）。

## 八、多卡与推理部署

- 多卡：loss scaling 策略不变。**NCCL 同时支持半精度和单精度**，所以梯度规约用哪种精度由开发者自选；batch size 相关约束跟随框架。
- 部署：训练完的模型用 **TensorRT** 做 GPU 推理优化，原文把这一步单列成一节，指过去即可。

## 九、原文给出的实测数据

同一份表格里既有精度也有吞吐，结论是"精度基本不动，速度看模型"：

| 模型 | 框架 | FP32 指标 | 混合精度指标 | 加速 |
| -------- | -------- | -------- | -------- | -------- |
| BERT Q&A | TensorFlow | 90.83 (SQuAD) | 90.99 | 1.94x（66.65 → 129.16 sent/s） |
| SSD w/ RN50 | TensorFlow | 0.268 mAP (COCO) | 0.269 | 1.32x |
| GNMT | PyTorch | 24.16 BLEU (WMT16) | 24.22 | 2.35x |
| NCF | PyTorch | 0.959 HR (ML-20M) | 0.960 | 1.81x |
| U-Net Industrial | TensorFlow | 0.965-0.988 | 0.960-0.988 | 1.10x |
| ResNet-50 v1.5 | MXNet | 76.67 Top1 (ImageNet) | 76.49 | 3.47x |
| Tacotron 2 / WaveGlow | PyTorch | 0.3629 / -6.1087 | 0.3645 / -6.0258 | 1.18x / 1.94x |

加速跨度 1.1x ~ 3.5x 正好印证第七节的结论：**矩阵乘/卷积占比越高的模型，收益越大。**

## 十、FAQ 里最该记住的五条

1. **精度会变差吗？** AMP 的设计目标就是与 FP32 精度一致，原文明说"实践中从未观察到明显的精度退化"。
2. **能加速多少？** 没有精确规则。线性层和卷积越大越快，**很小的层几乎无收益**；另外 AMP 省显存，可以趁机加大 batch 换取进一步加速。
3. **为什么我只快了 5%？** 先用 DLProf 分清是数据 IO 受限还是算力受限；再看 kernel 名里有没有 `[i|s|h]884`、`[i|s|h]1688` 这类标记（如 `volta_h884gemm_...`），确认 Tensor Core 真的被调用；然后检查该层是否被框架的 DenyList 挡住、维度是否 8 对齐。
4. **硬件门槛？** 必须有 Tensor Core。训练推荐 V100，推理推荐 T4。
5. **模型从 graph 看只有 FP32 类型？** 属于框架侧现象（DenyList/cast 时机），不代表 AMP 没生效 —— 以 kernel 名和实测吞吐为准。

## 十一、原文没讲、但必须知道的三种格式

原文（2023 版）只围绕 FP16 展开。如今的训练栈普遍有更省心的选择，横向对照如下（**这部分是补充，不属于原文**）：

| 格式 | 指数 / 尾数 | 动态范围 | 精度 | 典型硬件 / 场景 |
| -------- | -------- | -------- | -------- | -------- |
| FP16 | 5 / 10 | 约 6e-8 ~ 6.5e4 | 高 | Volta+，必须配 loss scaling |
| BF16 | 8 / 7 | 与 FP32 相同（约 1e-38 ~ 3e38） | 低（约 3 位十进制） | Ampere+，**范围与 FP32 一致，通常不需要 loss scaling**，是当前训练默认项 |
| TF32 | 8 / 10 | 与 FP32 相同 | 中 | Ampere+ 的矩阵乘内部精度，无需改代码，`torch.backends.cuda.matmul.allow_tf32` 控制 |
| FP8 | 4~5 / 2~3 | 很窄，需 per-tensor 缩放 | 很低 | Hopper+，多为推理或大模型训练的量化路线 |

选型的一句话原则：**先要范围（BF16/TF32），再谈位宽（FP8）；只有在没有 BF16 的老硬件上，才回到 FP16 + loss scaling 这一套。**

## 十二、落地清单

- [ ] 确认卡有 Tensor Core（V100 / T4 起），否则以上全部不成立
- [ ] 优先试框架原生 AMP（PyTorch 的 `torch.cuda.amp` 一类），不要一上来手写 cast
- [ ] 有 BF16 就先用 BF16，省掉 loss scaling 的整套调参
- [ ] 用 FP16 时：主权重留 FP32、BN 统计量留 FP32、descale 放在反向之后与梯度裁剪之前
- [ ] 优先选动态 loss scaling；用常数 S 时把 `S × max(|梯度|) < 65,504` 当作硬约束
- [ ] 形状对齐：batch、linear 维度、卷积通道、词表、序列长度都对齐到 8 的倍数
- [ ] 先 profile 再优化：DLProf 找瓶颈，kernel 名确认 Tensor Core 是否真的在跑
- [ ] 用混合精度省下的显存换 batch size，再测一次吞吐
- [ ] 精度回归用固定种子 + 固定验证集对比 FP32 基线，别只看 loss 曲线
